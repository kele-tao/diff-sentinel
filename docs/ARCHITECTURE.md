# Architecture

diff-sentinel is one pass over a parsed diff, a set of pure rule functions, and
a renderer. There is no plugin system and no AST rewriting: the whole pipeline
is ~2,800 lines of stdlib Python and every stage is a pure function you can call
from a REPL.

## Pipeline

    raw text / git range
          |
          v
    diffparse.parse_patch()      unified diff -> Diff(files -> hunks -> lines)
          |
          v
    classify.classify()          path -> area, language, is_test, is_doc
          |
          v
    rules.run_rules()            10 rule functions -> list[Finding]
          |
          +--> imports.build_import_graph()  (only for --base / --repo reviews)
          |         |
          |         v
          |    review.compute_impact()  -> list[ImpactEntry]
          |
          v
    scoring.compute_score()       findings -> 0..100 score + verdict
          |
          v
    render.render_terminal / render_markdown / render_json

## Modules

| module | lines | responsibility |
| --- | --- | --- |
| `diffparse.py` | 327 | unified diff parser: hunks, renames, binary, CRLF, quoted paths |
| `classify.py` | 208 | path classification table: risk area, language, test/doc detection |
| `rules.py` | 960 | the ten analysers and the 19 finding rules |
| `imports.py` | 228 | static import graph for Python (ast) and JS/TS (regex) |
| `review.py` | 115 | pipeline orchestration, ignore prefixes, impact map |
| `scoring.py` | 56 | penalty table, verdict thresholds, gate messages |
| `render.py` | 360 | terminal card, Markdown, JSON, GitHub Actions snippet |
| `cli.py` | 361 | argparse tree, exit codes, error translation |
| `catalog.py` | 102 | single source of truth for the rule list |

## Why these choices

**Parse the diff, not the repository.** A reviewer only needs to judge what
changed. Reading the diff keeps the tool fast on huge monorepos and means it
never executes or imports the code under review. The repository is read only for
the impact map, and then only with `ast.parse` (no execution).

**Rules are pure functions.** Every rule takes the same `ReviewContext` and
returns `list[Finding]`. There is no shared mutable state, so rules can be
tested one at a time with a five-line patch and they cannot interfere with each
other's output.

**Findings are structured, not formatted.** A `Finding` carries rule id,
severity, path, line, evidence, fix and detail. All three renderers consume the
same object, so `--format json` and `--format md` can never disagree, and CI
can gate on fields instead of scraping text.

**Impact map is breadth-first, capped.** `compute_impact` walks reverse
edges from every changed module with a depth cap of 8 and keeps at most 40
dependents per module. That bound is what keeps a 500-file diff under a second
even though the graph itself is rebuilt per run.

## Determinism

* All dictionaries that reach output are sorted before rendering.
* Findings are sorted by `(-severity, rule, path, line)`.
* `benchmarks/run.py` writes JSON with a fixed key order.
* The example patch is regenerated by `examples/make_patch.py` and CI asserts
  that the committed file is byte-identical (so the screenshot can be trusted).
